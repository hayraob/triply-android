PRODUCT VISION
Triply is a polished travel companion that helps people discover places, plan multi-stop trips, organize schedules, estimate routes, manage budgets, prepare for travel, and keep memories. It should feel like a thoughtfully art-directed travel product—not a generic AI-generated dashboard, a CRUD form application, or a collection of empty cards.

The product should make planning a trip feel enjoyable. The app must be visually rich but controlled, straightforward to use, responsive, accessible, and dependable on real Android devices.

LOCKED PRODUCT DECISIONS
- Product name: Triply.
- Build type: Native Android application.
- Platform: Kotlin and Jetpack Compose are preferred.
- Visual direction: Modern Travel Editorial.
- Map behavior: Online maps are the default; offline map downloads are optional.
- App languages: Indonesian and English, selectable by the user. English may be the initial default if device locale is unavailable, but Indonesian must be fully supported.
- Destination imagery: Real photographs from suitable online image sources, with graceful placeholders and caching.
- Place search / POI data: Hybrid provider strategy. Use appropriate data sources and a provider abstraction rather than relying on one incomplete source.
- Default currency: Indonesian Rupiah (IDR), with number grouping and currency formatting. Keep the data model extensible for other currencies if implemented.
- Trip creation: Guided step-by-step flow. Users may skip optional steps and edit previous steps.
- Local-first data: Core trip data must work without requiring user accounts or a custom backend.
- Local backup and restore must remain available.
- Group trip exchange in V2 should support export/import of a shared trip package (ZIP). Do not claim real-time cloud synchronization unless it is actually implemented with a secure backend.

DESIGN DIRECTION — MODERN TRAVEL EDITORIAL
Create a distinctive visual identity inspired by premium travel magazines, carefully art-directed travel publications, and high-quality travel applications. The UI should combine immersive destination photography, deliberate typography, strong composition, useful information density, and restrained motion.

Avoid the common visual patterns associated with low-quality AI-generated interfaces:
- Do not use the same rounded card for every piece of content.
- Do not fill every screen with generic cards, pills, gradients, and icon tiles.
- Do not use excessive purple/blue gradients, glowing borders, glassmorphism, or decorative blobs.
- Do not create huge empty spaces that make the app look unfinished.
- Do not use random stock photos unrelated to the location or category.
- Do not use emojis as substitutes for a coherent icon system.
- Do not use oversized headings everywhere or tiny low-contrast body text.
- Do not make every section symmetrical and identical. Use hierarchy and intentional variation.
- Do not make screens look like web admin dashboards squeezed into a phone.

Visual principles:
- Use a deep charcoal or deep navy foundation with layered surfaces.
- Use a restrained warm accent such as amber, ochre, or muted coral. Establish exact color tokens and use them consistently.
- Use a high-quality sans-serif type system with clear hierarchy and comfortable line lengths.
- Use real destination photography in meaningful contexts: destination discovery, trip headers, place previews, journal entries, and accommodation previews.
- Use varied but consistent layouts: editorial hero sections, horizontal destination rails, compact itinerary rows, image-led place cards, maps, timeline layouts, and data visualizations where they help.
- Give controls clear states: default, pressed, selected, disabled, loading, error, and success.
- Use shapes and corner radii intentionally; not every component needs a pill or a large rounded container.
- Provide sufficient contrast, readable text sizes, touch targets, and accessibility semantics.
- The result should feel premium, calm, useful, and recognizably designed—not merely decorated.

Before implementation, define a small design system including color tokens, typography scale, spacing, shapes, elevations, icon conventions, buttons, text fields, chips, sheets, navigation, loading states, and empty/error states. Apply it consistently across the whole application.

MOTION AND INTERACTION
Use subtle, purposeful motion rather than constant animation. Include:
- Smooth but quick navigation transitions.
- Natural bottom-sheet and modal transitions.
- Press feedback on interactive cards and buttons.
- Animated selection states in calendars and filters.
- Animated progress for budget and packing completion.
- Skeleton loading or appropriate progress feedback for network requests.
- Smooth transitions when adding destinations or itinerary items.

Animations must respect reduced-motion/accessibility considerations where practical and must not make the app feel slow. Avoid gratuitous looping animations.

PRIMARY NAVIGATION
Use a clear five-destination bottom navigation structure:
1. Explore — destination discovery, search entry point, popular categories, and inspiration.
2. My Trips — upcoming, active, and completed trips.
3. Create — prominent action to start the guided trip flow.
4. Budget — cross-trip financial overview and access to trip budgets.
5. Profile — settings, language, backup/restore, preferences, app information, and developer credits.

Keep navigation predictable. Do not hide essential actions behind obscure menus. Preserve state sensibly when moving between tabs.

MODULE REQUIREMENTS — ALL 12 ARE MANDATORY
All twelve modules below must exist in the delivered application. Do not silently omit a module. If a feature depends on an unavailable provider, implement a clear, honest fallback and communicate the limitation in the UI rather than showing fake data or a nonfunctional control.

1. TRIP BUILDER & MULTI-DESTINATION
Create a guided, enjoyable trip creation experience. It must not look or behave like a long employment/application form.

Required flow:
- Destination: search and select one or multiple destinations. Show useful place previews and real imagery when available.
- Dates: choose trip start and end dates with a visual calendar.
- Travel style: solo, couple, friends, family, or group.
- Transportation: motorcycle, car, train, bus, airplane, and other/custom options as applicable.
- Accommodation: search or select lodging when useful; this step must be skippable.
- Budget: set an overall budget and optionally allocate categories.
- Review: show a polished trip summary before creation.

Requirements:
- Users can go back and edit any completed step.
- Optional steps can be skipped.
- Validate required information with clear, friendly explanations.
- Support multiple destinations and their order.
- Avoid forcing users to type information that can be selected from a calendar, search result, or structured choice.
- Save drafts locally where appropriate.

2. MAPS, PLACE DISCOVERY & ROUTE ESTIMATES
Maps must work online immediately. Users must NOT be required to download an offline map before they can browse or search places.

Required behavior:
- Display an interactive online map with a clear loading state and graceful failure state.
- Search real-world points of interest, not just city and country names.
- Support relevant categories such as beaches, mountains, tourist attractions, villages, hotels, guesthouses, restaurants, cafes, shops, convenience stores, gas stations, ATMs, pharmacies, hospitals, and other useful facilities where provider data exists.
- Display useful place details: name, category, address or area, coordinates, available photos, provider attribution, and rating/opening-hours information only when reliable data is available.
- Allow users to select a place and add it to a trip or itinerary.
- Support route estimates between selected trip locations when a routing provider is configured and available.
- Provide map markers, camera movement to search results, and sensible result loading/error/empty states.
- Keep a provider abstraction for map tiles, geocoding, POI search, and routing. These are separate capabilities and must not be treated as one interchangeable API.
- Use a hybrid POI approach with a primary source and compatible fallback source(s), subject to licensing, attribution, rate limits, and terms of use.
- Do not scrape providers in violation of their terms. Do not assume that OpenStreetMap map tiles, OpenStreetMap POI data, geocoding, and routing are the same service.
- Respect provider rate limits. Debounce search input, cache suitable results, avoid excessive requests, and handle unavailable providers.
- Online map and place search should remain the default. Offline region downloads are an optional additional feature.

Offline map downloads:
- Let users choose a supported region and see estimated download size where possible.
- Explain what will and will not be available offline.
- Store downloaded map data safely and provide delete/manage controls.
- Never imply that downloaded map tiles automatically include live search, routing, live traffic, or current business information.

3. BUDGET & EXPENSE TRACKER
Make financial entry simple and legible.

Required behavior:
- Format IDR values automatically with Indonesian thousands separators. Example: typing 150000 should display Rp150.000 or an equivalent consistent presentation; typing 1500000 should display Rp1.500.000.
- Do not require users to type periods, commas, or currency symbols manually.
- Store amounts as numeric values in the data layer; do not store formatted display strings as the financial source of truth.
- Support overall budget, categories, transactions, transaction notes, dates, and optional payer/member information.
- Provide useful totals, remaining budget, category summaries, and clear progress visualization.
- Make it easy to add an expense with minimal taps.
- Warn users when they approach or exceed a budget threshold, with non-alarming language.
- Do not fabricate exchange rates. If currency conversion is provided, use a reliable live source and show update/source information. IDR remains the default.

4. ALARM & TIMELINE
- Present an itinerary timeline grouped by trip day.
- Support activities, start times, notes, and locations.
- Allow reminders for relevant activities and departure times.
- Request Android notification/alarm permissions contextually and explain why they are needed.
- Handle Android scheduling restrictions and denied permissions gracefully.
- Do not claim that reminders are scheduled unless Android confirms the operation.

5. PACKING CHECKLIST
- Provide useful categories and editable packing templates for general travel, hiking, beach trips, and other relevant travel styles.
- Allow custom items, quantities, notes, and completion states.
- Display animated but restrained completion progress.
- Keep checklist data available offline.

6. ACCOMMODATION & TRANSPORTATION
- Support discovery/search for accommodation and transportation options where suitable providers are available.
- Allow users to save manually entered bookings or options even if no booking integration exists.
- Store name, address, contact details, date/time, price, notes, and external booking URL where available.
- Add relevant costs to the trip budget without double-counting.
- Clearly distinguish a real provider result from a user-entered saved record.
- Do not claim to book or reserve anything unless a real booking integration exists and confirms success.

7. WEATHER ALERT
- Show weather forecasts for trip destinations and dates when supported by the weather provider.
- Present temperature, precipitation probability/amount, and useful condition descriptions where available.
- Indicate when forecast data was last updated.
- Handle unavailable or out-of-range forecasts honestly.
- Provide warnings when the weather provider reports relevant severe conditions; do not invent alerts.

8. EMERGENCY CENTER
- Provide emergency contact shortcuts and configurable personal emergency contacts.
- Show useful emergency information and nearby facilities when online location/POI services are available.
- Ask for location permission only when the user invokes a location-dependent feature.
- Clearly distinguish official emergency numbers from user-added contacts and general nearby services.
- Never fabricate emergency phone numbers. Verify country-specific numbers and provide a way to edit or review them.
- Do not automatically contact anyone without explicit user action.

9. TRIP JOURNAL
- Allow users to create dated trip notes and attach photos.
- Associate entries with trip days and optional locations.
- Provide an attractive photo-led journal/album layout.
- Keep entries locally available and included in supported backup/export operations.
- Handle Android photo/media permissions using current platform guidance.

10. GROUP MANAGEMENT
- Support group member records, roles or labels, shared packing/task lists, and expense attribution.
- Support export and import of a shared trip package as a ZIP file.
- Include the trip data needed for a useful portable package, with clear handling of attached photos and metadata.
- Validate imported packages, handle duplicates/conflicts safely, and show an import summary before changing existing data.
- V2 does not require real-time multi-device synchronization or a custom cloud backend. Do not fake synchronization.

11. OFFLINE MODE
- Store core trip data locally using a reliable persistence layer.
- Allow access to saved trips, itinerary, budget, packing lists, and journal entries without internet.
- Cache appropriate images and network results while respecting provider rules and storage limits.
- Communicate which features need internet and which are available offline.
- Avoid data loss when connectivity changes.
- Provide clear backup/export and restore/import paths.

12. WHAT IF PLANNER
- Let users explore alternative dates, routes, transportation choices, destinations, or budgets.
- Compare the alternative with the original plan in a clear side-by-side or structured summary.
- Mark estimated values as estimates and show their source when available.
- Do not silently alter the original trip. Users must explicitly apply a proposed alternative.
- Never fabricate live prices, route availability, or weather information.

LANGUAGE & LOCALIZATION
Implement full Indonesian and English localization from the beginning. Do not hardcode user-facing text throughout composables.

Requirements:
- A user can change language in Profile > Settings > Language.
- Apply the selection consistently to all screens, dialogs, validation messages, notifications, date labels, and relevant accessibility descriptions.
- Persist the user's language choice.
- Use locale-aware date and number formatting.
- Indonesian is a first-class language, not a partial afterthought.
- Avoid mixing Indonesian and English in the same screen unless a proper name or source-provided term requires it.

PROFILE, SETTINGS & MAPS/API CONFIGURATION
Separate everyday settings from developer configuration.

Normal user settings should include:
- Language.
- Currency preference (IDR default).
- Map appearance where supported (for example standard/dark/satellite, only when the chosen provider actually supplies those styles).
- Online map preference and mobile-data preference.
- Offline map region management.
- Location and notification permission status with clear explanations.
- Backup and restore.
- Privacy information and app information.

Do NOT show ordinary users raw API-key fields for map tiles, routing, geocoding, POI, or weather. Users should not have to register for developer accounts just to use Triply's basic maps or place search.

Provider/API configuration belongs in a developer/advanced area or secure build/deployment configuration. The app must select sane default providers automatically. If a provider requires credentials, use a secure and appropriate architecture:
- Never commit private API secrets to the repository.
- Never expose server-side secret keys in the APK.
- Restrict public client keys by package/signing identity and provider capabilities where supported.
- Use a backend/proxy for secrets that cannot safely live in a client application, if required and available.
- Document setup, quotas, costs, attribution, and provider limitations.
- Provide graceful fallback when an optional service is not configured.

The app must not show a misleading "connected" status when a service has not been tested successfully.

- Request only necessary Android permissions, at the point they are needed.
- Do not collect or transmit trip data unnecessarily.
- Document network services and data shared with providers.
- Validate imported ZIP content and guard against unsafe paths, oversized files, malformed data, and unsupported versions.
- Handle backups and restores without silently overwriting valuable user data.
- Include privacy and third-party service documentation.

TECHNICAL IMPLEMENTATION
Use a maintainable native Android architecture. Preferred stack:
- Kotlin.
- Jetpack Compose and Material 3 foundations, customized with the Triply design system.
- Room for local persistence.
- Kotlin coroutines and Flow for asynchronous data operations.
- WorkManager and appropriate Android alarm/notification APIs where needed.
- MapLibre Native or another technically justified native map renderer, selected after checking current Android compatibility and provider terms.
- Repository/service abstractions for map tiles, geocoding, POI, routing, weather, and image sources.
- Dependency injection only where it improves maintainability; avoid unnecessary complexity.

Technical requirements:
- Use clear feature/module boundaries and predictable state handling.
- Keep UI, domain logic, persistence, and network/provider code separated.
- Use stable, testable data models.
- Handle lifecycle, configuration changes, permissions, and process recreation.
- Avoid blocking the main thread.
- Use pagination or bounded result sets for place search where appropriate.
- Handle network timeouts, provider errors, offline state, and retries responsibly.
- Provide meaningful logging for development without logging secrets or sensitive trip data.
- Keep Gradle dependencies compatible and avoid speculative or abandoned libraries.
- Check current provider and Android documentation before committing to a library or API integration.
